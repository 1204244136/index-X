# 工具簇合同与文档边界重构（2026-10-09）

## 范围

`tools/README.md` 的结构重排、`check_project_docs.py` 的工具簇合同，以及跨层文档边界的收口。**未修改任何 EPUB 内容**，未执行发布与上传；62 个工具/配置的数量与文件名均未变动。

## 起因与判据

原 README 同时使用两套轴：`## 职责与覆盖矩阵`（按工具，37 行承载 62 条，其中 10 行是一行多工具，最重的一行 16 个共享模块）与正文按阶段的四节。同一工具在两处用不同顺序、不同颗粒度出现，且存在错归类：`manifest.py`、`publish_preflight.py` 带 `__main__` 却被登记为「共享模块」，`publish_preflight.py` 在文件内出现 3 次；会写盘的 `text_norm.py` 挂在「只读检查与诊断」下。

判据沿用 `tool-responsibility-cleanup-2026-09-19.md`：**「命令数量和文件长度不单独构成删除或拆分理由」**，冗余只按「同一规则多处实现、共享能力寄居在不相关入口」认定；另补两条可机械判定者——(a) 同一能力两个入口且判定语义无差别；(b) 零外部引用 + 零专用测试 + 不属任何流程步骤。

## 结论

| 项 | 结论 |
| --- | --- |
| 簇的切分 | 按**用途**为主轴，按数据流顺序排列，写入风险降为簇内标签，共 6+1 簇：C1 同步与发布(7)、C2 导入与交稿往返(13)、C3 成品结构与配对修复(10)、C4 门禁与体检(10)、C5 内容质量(4)、C6 检索与统计(4)、C0 共享内核(14) |
| 归属唯一性 | 每工具只属一个簇：有 `__main__` 的 `.py` 进 C1–C6，无 `__main__` 的进 C0；`pull.ps1` 与两个 BW 配置 JSON 按消费它们的入口簇归属。`manifest.py`、`publish_preflight.py` 因此迁出「共享模块」并入 C1，原双重登记消失 |
| 三层边界 | AGENTS = 规范与边界的唯一来源；`tools/README.md` = 命令合同（入口、参数、读写范围、门禁与失败边界、测试、簇归属），不复述规则只留指针；`.agents/skills/` = 流程与判断分支 |
| 路由与预案 | 新增 `## 路由`（12 条意图入口）与 `## 阻塞与恢复`（P1–P7 七条预案，含触发信号／判定命令／允许／禁止／簇／证据留档）。预案是「工具停下来 + 有明确禁止动作」的处置，不是 skill |
| 冗余认定 | **可删工具为零**：6 组候选逐一核实后全部保留（能力互缺或判定语义正交），14 个「零外部引用」工具中 8 个被其他 tools 代码 import、6 个是有 CLI 与合同的只读入口，孤立件为空集 |

## 文档边界的机械保障

`check_project_docs.py` 的矩阵唯一性检查被替换为**工具簇合同**，六条均可触发失败：

1. 每个 `tools/` 顶层文件在恰好一个簇成员表出现且只出现一次（成员表列固定为「工具｜入口命令｜读写范围｜门禁与失败边界｜测试」）；
2. `## 簇索引` 覆盖全部簇，每簇登记的入口数与成员表行数一致；
3. C1–C6 的行必须给出反引号入口命令，C0 的行必须写「无 CLI」；配置类无 CLI 者显式写「无 CLI」；
4. 「门禁与失败边界」列必须以 `【P<n>】` 指向预案或写 `【无】`，引用的预案必须已定义；
5. `## 路由` 中出现的工具名必须存在于某个成员表；
6. 找不到 `## 簇索引` 或任何簇节时报错——**不再静默返回空**（原实现在标题被改名时会静默失去门禁）。

`tools/` 目录为空时不执行簇合同检查（没有可登记的成员）。

## 陌生读者实测

把重排后的 `tools/README.md` 单独交给一个不知背景的子智能体（只允许读该文件），按六道固定题定位入口与处置：**6/6 命中**。实际检索路径是「路由 → 阻塞与恢复 → 簇节」，**没有一题需要先读簇索引**；簇索引被读作「各簇管什么／几个入口／主要门禁」的汇总表，而不是导航。

实测报出 12 处犹豫点，当场修掉 5 处真缺陷：

| 缺陷 | 修法 |
| --- | --- |
| 路由表把「中日结构／行数对不上」整行写成 C3，而 P4 写「C4 查→C3 修」 | 路由行改为 `C4 查 → C3 修`，并列出两侧的实际入口 |
