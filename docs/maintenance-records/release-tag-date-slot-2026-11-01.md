# 发布标签日期口径修复（2026-11-01）

- 范围：`.github/workflows/build-epub-release.yml` 的发布元数据、重复发布守卫、标签与时序；`README.md` 下载渠道说明。
- 背景：提交 `20c6635d` 同时带 `2026.10.31` 与 `2026.11.01` 两个日期 tag，两次 release 各 87 个资产、各 1,028.9 MB，内容为同一棵树。该提交是 10-30 22:40 的工具改动，10-31 全天无提交；11-01 的三个正文修订（`bd0abdf4`、`5ccc51d0`、`3d348b33`）都在两次发布之后才入库。

## 根因

- 工作流 cron 为 `0 15 * * *`（UTC 15:00 = 北京时间 23:00），但 GitHub 计划任务近 5 次实际启动延迟 233–296 分钟，全部落在北京时间次日 03:42–03:55。
- 原「Prepare release metadata」在作业启动时刻用 `TZ=Asia/Shanghai date` 取日期，跨过零点后标签整体推到次日：10-30 19:45Z 的运行标为 `2026.10.31`，10-31 18:53Z 的运行标为 `2026.11.01`。
- 工作流没有重复发布守卫：当天没有新提交时，相邻两天的运行仍各建一个标签与 release，指向同一提交。
- 打包把 checkout 的文件 mtime 写进 zip 条目，同内容重建的摘要也不同（`S0_00.epub` 两侧均为 397,503 字节但 sha256 不同），重复发布无法靠摘要识别。

## 修正

- 标签日期改按「计划发布日」推算：取最近的 15:00Z 计划槽位，UTC 日期与北京时间 23:00 同日，计划任务延迟到次日不再改变标签；`workflow_dispatch` 新增 `release_date` 输入可显式指定。
- 新增「Check whether this snapshot is already published」守卫：当前提交已带 `YYYY.MM.DD` 标签时跳过构建与上传；`workflow_dispatch` 的 `force_release` 可强制重发。
- 同日补充发布保留原 release，`removeArtifacts` 改为 `replacesArtifacts` 逐项替换，不再整批删除资产；标签移动改到资产上传成功之后，上传失败时下一次运行会重试；新标签由 release action 按 `github.sha` 创建。
- `README.md` 同步说明「定时检查、有新提交才发布」与「标签按计划发布日命名」。

## 限制与维护

- 现有的 `2026.11.01` 与 `2026.10.31` 重复发布暂不删除；修复推送后，下一次运行会把 `2026.11.01` 移到 11-01 的最新提交并按新内容替换资产。
- 守卫以「当前提交已带日期标签」判定已发布：若 release action 建好标签后上传中断，需用 `force_release` 手动补发。
- 只覆盖延迟小于 23 小时的情况；超过一天的极端延迟仍会落到上一个槽位。
- 打包仍未固定 zip 条目时间，同内容重建的摘要差异仍在；需要摘要级去重时再单独处理。
