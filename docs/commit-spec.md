# 提交规范

文档职责与入口见 [文档索引](README.md)。本文件是本仓库提交标题、正文、执行核验与对话收尾格式的唯一来源；`AGENTS.md` 管提交权限、文件边界与同步前提，各 skill 管业务流程与完成条件。编写、检查或重写提交信息时必读本文件。

## 一、提交单元

一个提交表达一个可独立说明、验证和回退的结果。围绕同一内容修订产生的裁定与维护记录随成品同批提交；独立的工具、规范维护与 EPUB 修订分开提交。文件是否同批由任务关系决定，不按目录机械拆分。

提交信息根据最终暂存差异编写；历史提交只作参考，遇到与本规范不同的格式以本规范为准。仅用户指定的历史提交可在核对分支与工作区后重写，不为统一风格批量改写历史。

## 二、标题

```text
<type>(<scope>): <中文摘要>
```

标题遵守 Conventional Commits。`type` 与 `scope` 用小写英文，括号、冒号用半角，冒号后一个空格。每次只选一个 scope，表示稳定职责域；作品号、书名、术语与本次批次均写在摘要中。

| type | 使用条件 |
| --- | --- |
| `fix` | 修正已有译文、成品、工具或自动化行为的错误；整卷通校与校对复核也属此类 |
| `feat` | 新增收录作品或新增工具能力；不按修订规模判断 |
| `refactor` | 调整工具内部结构，外部行为保持不变 |
| `docs` | 只修改规范、skill、说明或记录 |
| `test` | 只新增或修正测试 |
| `ci` / `build` | 维护自动化／构建与依赖机制，如调整触发条件、执行环境或构建配置 |
| `chore` | 不属于以上类型的仓库维护；能归入前项时使用前项 |

纯文档变更（含规范或 skill 的错误订正）统一用 `docs`；有运行行为变化时，修错／新增能力优先用 `fix`／`feat`，机制维护再用 `ci`／`build`。

| scope | 职责域 |
| --- | --- |
| `epub` | `EPUB/` 成品，包括正文、包装、图片、元数据与排版；随附裁定／记录仍用此域 |
| `tools` | 维护工具及其测试、附带命令合同 |
| `skills` | `.agents/skills/` 的流程与契约 |
| `spec` | `docs/` 中的规范正文 |
| `docs` | 读者说明、文档索引与维护记录等其它文档 |
| `ci` / `build` / `deps` / `repo` | 自动化／构建／依赖／仓库级配置与规约 |

优先复用表中 scope；确有独立、长期维护的职责域时才新增小写英文名称。多域同批按主要结果选择 scope，附带入口、测试或合同沿主域，不按文件数决定、不增加第二个 scope。`fix(S1_01)`、`fix(EPUB)`、`fix(epub,docs)` 均不用于新提交。

摘要写清对象与最终结果：用「修正」表达错误订正、「统一」表达术语收敛、「导入」表达新书收录。避免只写「图片调整」「优化」「更新」；不用完整书名、多个案例或细分数量堆叠标题，不加句末句号。优先压到 72 个字符以内，完整作品号与必要术语优先保留。

EPUB 摘要按「范围 + 空格 + 动作与结果」排列：单本范围用完整作品号（`S1_01`、`S5_03_02`、`S6_YY.MM.DD`）；跨本写 `<N> 本`，正文列全编号。推荐形态如下，术语和动作据实际结果填写：

```text
fix(epub): S1_01 修正茵蒂克丝张开双臂的动作描写
fix(epub): 8 本 统一「古き善きマリア」译名为「玛丽亚」
feat(epub): S5_04_02 导入中文成品
fix(tools): 修正相同改动被误判为同步冲突的问题
docs(skills): 统一校对复核报告契约
```

校对复核固定使用下列两种标题：有复核追加回改／规范化时用第一种，没有追加修正但有原批次待提交时用第二种；不混用「通校优化／复审／落库／落地」命名同一流程。

```text
fix(epub): <范围> 校对复核与修正
fix(epub): <范围> 校对复核确认批量修订
```

## 三、正文

标题后空一行，正文统一使用 `- 字段：内容`。每个字段一项，按下表顺序选用；同一事实只写一次。所有提交至少有「范围、修正、验证」，EPUB 内容修订另有「依据、同步」；校对复核用「复核」承载依据。其它条件字段只在适用时出现。

| 字段 | 内容与适用条件 |
| --- | --- |
| 范围 | 完整作品号／工具／文档范围，实际暂存文件数；批量内容改动交代基准与提交对象 |
| 依据 | 内容修订给实际读取的日文短句、上下文或规约条款，并解释为什么需要改；工具／文档在需要解释原因或取舍时填写 |
| 复核 | 仅校对复核使用，字段内容按下一节；不把单点订正包装成整卷复核 |
| 修正 | 最终行为或旧→新，以及必要的数量、边界与保留项；不写已撤回的尝试或操作流水账 |
| 验证 | 实际运行的命令、关键参数、范围和结果；未执行、失败或未配对范围如实说明，不能只写「全部通过」 |
| 同步 | EPUB 内容修改的实际同步命令、范围与结果；无新增发布时写已一致，不虚称发布了作品；纯工具／文档提交省略 |
| 留档 | 按 `AGENTS.md` 需要维护记录时给仓库相对路径；新裁定在依据／修正中引用裁定表条目 |

正文应能脱离本地缓存报告理解。单本没有维护记录时，把关键位置、最小改动与判断依据写进提交；跨本用概括结论配合维护记录承载细目。必要原文只摘短句，不搬运全量逐行报告，不用 `.cache/` 或机器绝对路径作为唯一证据入口。

数字取自本次实际暂存范围和有效报告，写明单位：文件、片段、去重位置、规范化命中分别统计。命令保留关键范围参数，历史数值与历史验证结果不能照抄成本轮结果。

### 校对复核

业务计数及覆盖判据的唯一来源是 [复核契约](../.agents/skills/proofread-review/references/review-contract.md)。按通用字段顺序写「范围 → 复核 → 修正 → 验证 → 同步」，跨本再加「留档」；字段需覆盖：

- 范围：EPUB 文件数及其中 XHTML 数，工作区基准 SHA／历史提交列表，以及提交包含整批校对修订及追加修正，还是仅历史复核的追加修正。
- 复核：总片段 T、有效规范级 S、语义级 M、切片数、保留新译 K、确认误改 R、待人工 H、未覆盖 U；必要的保留／否决依据。只有契约的完成条件成立才写复核完成。
- 修正：追加回改的去重位置数、主要问题类型、必要的短例与依据、规范化命中数及回改验收结果；无追加回改也要明确。原通校修订与追加回改分别交代，不把整批提交只描述成追加修正。
- 验证：除实际门禁外，交代术语比对及呼应核查范围、候选已判定数／总数与结果。

### 术语统一与成品导入

- **术语统一**：依据引用日文锚点与生效裁定／规约；修正交代取形、义项边界、实际替换数及未统一的保留项。跨本编号列在范围中，裁定与维护记录按各自职责引用。
- **成品导入**：依据交代交稿、图片素材及日文卷等来源；修正交代正文／包装／图片等成品构成、实际结构处理与数量；验证和同步写实际门禁与发布结果。

## 四、提交执行与核验

1. 核对本轮提交权限与业务前提，记录 HEAD、工作区及原有暂存状态；按任务关系确定提交单元。本规范只规定提交方式，不新增同步、发布或历史重写授权。
2. 只暂存本任务文件或补丁，同文件混杂改动按补丁隔离，保全其它任务的暂存状态。核对 `git diff --cached`、`git diff --cached --stat` 和 `git diff --cached --check`：范围与统计吻合，且没有临时产物或无关修改。
3. 根据暂存差异逐字段检查标题与正文：type／scope、完整作品号、最终结果、计数口径、实际验证与同步事实均一致。无版本化变更不创建空提交；前置门禁或同步失败按业务流程处理，不能用提交绕过。
4. 多行提交信息写入系统临时 UTF-8 文件，使用 `git commit -F <文件>` 保留真实换行；不把字面量 `\n` 当换行，不因命令转义困难改用英文或删掉正文。
5. 成功后用 `git show --stat --oneline HEAD`、`git log -1 --format=%B` 与 `git status --porcelain=v2` 核对实际 SHA、标题／正文、文件范围和剩余工作区状态。提交失败报告失败原因，不能把「已生成提交信息」写成「已提交」。

对话收尾报告每个实际提交的短 SHA 与完整标题、验证摘要、剩余改动（或工作区干净）及是否推送；不重复整份提交正文。
