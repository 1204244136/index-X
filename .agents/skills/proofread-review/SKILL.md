# 校对复核工作流（index-X）

文档职责与入口见 [文档索引](../../../docs/README.md)。

处理「校对工具改完，要判断改得对不对」这一类任务。仓库级规约以 `AGENTS.md` 为准，译文规范以 `docs/translation-spec.md` 为准，本文件写「怎么复核、怎么下判定」。

典型触发：外部 AI 辅助校对工具产出确认结果、应用到 `EPUB/` 之后，需要找出其中**误修改**并回改。

默认执行 R0–R7 的完整流程，直至主智能体（Lead）完成本地提交。用户明确要求「只读复核」「先报告」或「暂不提交」时，按该边界执行并在报告中写明；维护本 skill 本身不触发 EPUB 同步与提交。

## 一、先分清任务类型

| 任务 | 归属 |
| --- | --- |
| 复核成批、近重译级的译文改动（工作区未提交或已提交），判定每处改动的对错 | **本 skill** |
| 同一日文锚点的异译收敛、术语／口癖／敬称裁定 | `translation-term-unification` skill |
| 结构、行模板、中日对齐、图片行 | [EPUB 结构规范](../../../docs/epub-structure-spec.md)＋ `check_alignment.py` |
| 标点／字形等字符级规范化 | `tools/text_norm.py`（复核时属 `spec` 级，可批量放行） |

判据：改动是**批量的**、需要判断「改得对不对」，而不是「该改成哪个词」。

## 二、十条复核纪律

1. **只回原文**。判定依据是日文原文，不是中文两版谁读着更顺、也不是与台版／网翻比对。
2. **分级处置**。规范级（`spec`）确认类型后可批量放行；语义级按 R3 全量逐条核对，未实际回查的条目只能记「未覆盖」。Lead 对子报告的抽检不代替逐条核对。
3. **删减是误删实义成分的高发区**。工具会单独统计「明显删减（old−new ≥ 5 字）」，那批必须重点核；明显增删属于交叉风险标签，不能与片段总数相加。
4. **事实层优先**：数字、单位、专名、否定、时态、行为主体、词义方向（正／反）逐条核——改错的代价最大。
5. **术语改动比对规约与已裁定口径，不只看日文字面**。历史案例：校对把「科学阵营／魔法阵营」改成「科学侧／魔法侧」，字面贴近日文 `サイド`，但违反术语分层规约（`サイド`→阵营、指示层 `側`→侧）。**通校／重译类整批改动是这条的高危区**：逐句回原文重写会把用词改动淹没在 `rewrite` 里，只挑「看着像术语」的条目去比规约必然漏检。批量改动一律做**全量比对**，三处来源都要扫：`docs/translation-name-rulings.md`（按「裁定」列锚点扫日文命中行、按硬禁用写法扫新译，专查「已裁定正字 → 被否决写法」的回退）、`docs/translation-name-selection-spec.md`（§一 从俗已选定名单、§四 防日语中转）、`docs/translation-spec.md`。历史案例：创约9通校把已按裁定修好的「坏女人」改回硬禁用的「恶女」6 处，又把 `ダイアン＝フォーチュン` 按片假名逐字音译成「黛安·福琼」2 处——后者违反选取规范 §四（该名须原语还原为 Dion Fortune，§一 已选定「迪翁·福春」），是按日文记音直译的典型失手。
6. **写「建议回改」前，必须确认引用的原文行号与被引句子一致；更不得据旧译反推原文**。历史案例一：报告称 Epilogue L101 漏译「全裸」，引用的其实是 L83 的原文，L101 的译文本来正确。历史案例二：创约9复核据旧译「迪翁」反推日文为 `ディオン＝フォーチュン`，实际全库 318 处一律作 `ダイアン＝フォーチュン`——结论虽因选取规范 §四 而成立，写进报告与提交信息的理由却是错的。**凡要引用的日文，必须用 §七 的脚本把该行实际打出来。**
7. **原文刻意的省略、留白、悬念不许补**。历史案例：`だから彼らは気づかなかったのかもしれない。`（宾语由后文揭示）建议「补上宾语」会错误指代前文并破坏悬念——否决。
8. **否决也是结论**，要写清理由与依据；证据不足时转人工并写明缺什么，不猜、不将就放行。
9. **同一句说法在一个作品里必须前后一致——改动前后都要查「呼应」**。前后呼应（后文引述前文台词、叙述回指前文说法、同一句复现、角色口癖复现）的任一侧被改动，另一侧必须同步；只改一侧就会断裂，而**这类断裂不违反任何既有门禁**：行数、模板、XML、加粗、术语裁定全部照常通过。它比误改更隐蔽：误改是「这一处错了」，呼应断裂是「两处各自都对、放在一起矛盾」。历史案例（2026-10-14，S1_01）：
   - 日文同一句 `『……、じゃあ。私と一緒に地獄の底までついてきてくれる？』` 在本卷出现 3 次（Ch1 L411 原句、L706 与 L988 两处引述）；通校只改了 L411、L706，L988 留在旧译「即使我下地狱，你也愿意陪着我？」，同一句话出现 3 种中文。
   - 上条引述茵蒂克丝台词「还说什么『伤不了一根汗毛』」：被引述的原句在别处已经改成「连一道伤痕都留不下」，引述处未同步，读者会看到引述的内容与前文原句对不上。
   - 序章「要不帮一把吧——」（日文刻意省略宾语，后文 `但上条可不记得说过『要救那女孩』` 才揭示）被补上宾语「她」，直接毁掉叙述诡计。
   **做法**：`python tools/check_echo.py --book <作品号>` 定位三类候选（同一日文片段中文不一致／日文相似行对／日语侧引述回指；类 1 会按**实词／语体／虚词**标注差异性质并据此排序），然后按 §五 R3.5 逐条回原文判定。候选少不等于没有断裂——引述点靠机械信号只能覆盖一部分，改动集中的卷必须整卷核。反面口径：不构成呼应的相近句式要写明理由排除，**不得为凑对称把本来该不同的两处改成一样**。
10. **「中文不一致」不等于「必须统一」——判断依据是日语侧的语气层**。同一句日文在不同语境（说话人语体、随口与庄重、叙述与台词）下用不同中文，只要各自与原文相称就是合法的；机械候选里的「语体」类（如 `女の子` 译「女孩」与「少女」）**先核日语侧是随口还是誓言，再决定动不动**。历史教训（2026-10-14，S1_01 序章）：分片建议「三处统一为少女」只做了中文措辞比对、没核日文语气，我据此把 `『女の子を助けよう』とか言った覚えはない`（否认「说过那种话」）的引语从「要救那女孩」改成「要去救那个少女」，把随口的话抬成郑重表态，反而毁掉 L54 的反讽，事后回退。
    - **所以子智能体的措辞类建议一律要回原文复核后才可落地**：它给的「统一为 X」若依据只是「中文两侧不同」，那不是依据；依据必须是日语侧同形或引述关系，且新写法在语气层与原文相称。
    - **同理，工具的分类只是提示**：`实词` 不必然是异译（同义改写也会命中），`虚词` 也不必然能并存；分类决定回原文时该看什么，不决定要不要改。

## 三、输入形态与命令

改动来源：外部 AI 辅助校对工具的确认结果导出（`out/projects/<id>/snapshots/<ts>/translation-compare.csv`，列含 `jp` / `cn`）经应用后落到 `EPUB/`。**复核入口是 git 改动**，与应用方式无关。

```powershell
# 工作区未提交的改动（校对结果刚应用、还没提交）
python tools/proofread_review.py --worktree
python tools/proofread_review.py --worktree --path "EPUB/【S3_01】创约 某魔法的禁书目录 01"
python tools/proofread_review.py --worktree --out .cache/epub-work/proofread-review-s301

# 已提交的批量校对（可一次给多个提交）
python tools/proofread_review.py b7515335 2d44cb26 821c46b9 7a218119
```

产物（默认 `.cache/epub-work/proofread-review/`）：

| 产物 | 内容 |
| --- | --- |
| `changes.tsv` | 全部片段：`commit / work / file / line / grade / kind / old / new` |
| `semantic.tsv` | 需要回原文判断的片段（`tiny` / `local` / `rewrite`） |
| `spec.tsv` | 规范确定性改动，可批量放行 |
| `groups.txt` | 语义级按最小差异聚类，重复改动模式一眼可见 |

终端另给：片段数、各级别条数、`spec` 子类分布、**明显增补／明显删减**条数、按作品分布。

- **不要为复核新建 git worktree**：工具直接读 git 历史，`<commit>` 参数即够。
- 分级判据与参数的权威定义在 `tools/README.md`「提交级校对复核」与 `tools/proofread_review.py` 源码；本 skill 只写怎么用、怎么判。
- `.cache/` 属只读分析区，工具产物（TSV / `groups.txt` / 复核报告）落在其下的 `proofread-review/` 即可，**不进仓库**；也不要把报告写进其它 agent 的工作目录。
- 每轮显式指定 `--out .cache/epub-work/proofread-review/<run-id>`，该目录记为 `<report-root>`，不同轮不覆盖输入与报告。冻结清单、子报告字段及主报告模板的唯一来源是 [复核契约](references/review-contract.md)：R1 建清单、R3 派发、R7 汇总时均须读取对应部分。

## 四、分级与处置

| 级别 | 含义 | 复核处置 |
| --- | --- | --- |
| `spec` | 改动由 `docs/translation-spec.md` 条款决定（`punct` 标点排版 / `quote` 引号体例 / `glyph` 全半角 / `erhua` 去儿化 / `particle` 规范语气词） | 批量放行；只确认子类与规范一致，不逐条回原文 |
| `tiny` | 最小差异 ≤ 2 字且差异两侧全是虚词 | 仍要回原文，但一眼能看完；**不是「可跳过」** |
| `local` | 最小差异 ≤ 12 字（术语、用词、数字） | 逐条看，按 `groups.txt` 的聚类批量核同类 |
| `rewrite` | 最小差异 > 12 字，或整段增删 | 全量逐条回原文；重点检查信息增删、主体与逻辑方向 |

两条容易被误用的口径（工具已实现，复核者别用直觉覆盖）：

- **数字与字母不是标点**：剥标点判「只动了排版」时不能把 `0-9a-zA-Z` 一起剥掉，否则「删掉／改掉数字」会被静默放行——那正是事实性纠错的高发区。
- **`tiny` 不能只看字数**：「念动力 → 念动能力」「第10位 → 第位」最小差异都只有 2 字，却是术语与事实改动。

## 五、复核流程 R0–R7

**R0 圈定范围**：确认复核哪些提交／工作区改动、涉及哪些作品，以及任务是完整流程还是用户限定的只读／暂不提交。记录基准 SHA、已有工作区与暂存区状态，圈出本任务文件及混杂改动；同时记下零散订正／近重译级通校的性质，决定呼应检查范围。

**R1 跑工具、记基线**：按 [复核契约](references/review-contract.md) 冻结本轮工具产物、日文参考版本与 `manifest.tsv`，为每个片段分配稳定 ID。后续切片、判定与统计全部回指该清单；输入或参考内容变化则建新轮，不沿用已失效的行号与判定。

**R2 放行规范级**：核 `spec.tsv` 的子类分布是否符合规范条款，记录适用条款及片段 ID；掺了语义成分却落到 `spec` 的，保留原 ID、将清单的有效级别改为 `local` 后纳入切片。重分类在派发前冻结。

**R3 分层核对语义级**（按风险从高到低；**一律按 §六 强制切片并行**，分级判据与三种出口不变）：

1. 事实层：数字、单位、专名、否定、时态、主体、词义方向 —— 逐条回原文；
2. 明显删减 → 重点核（误删高发）；明显增补 → 确认不是凭空添加；
3. 术语改动 → 对照 `docs/translation-name-rulings.md` 的已裁定结论与 `AGENTS.md` 口径；发现应新增裁定时只提出候选与依据，不自行写入裁定表；
4. `groups.txt` 聚类里的高频模式 → 同类组织核对，可共用规范依据，但每个 ID 仍须核实际日文与上下文；
5. `rewrite` → 全量逐条核对，重点看有没有整段删掉信息。

风险池（§6.3 第 1 行）必须独立成片；`spec` 级已在 R2 放行，不派子智能体。**语义级一律派片，不得以「量小」「一眼能看完」「先自己过一遍」为由由 Lead 自办。**

**R3.5 呼应检查（逐处判定之后做，独立于批次改动）**：R3 判的是「这一处改得对不对」，呼应检查判的是「同一句说法在作品内还一致吗」。两者都要做——一处改得完全正确，仍可能让后文引述它的地方变成孤儿。

- **入口**：`python tools/check_echo.py --book <作品号>`（可重复 `--book`）。输出三类候选：同一日文片段在作品内出现多次而中文译法不一致（片段多译，按**实词／语体／虚词**标注差异性质并据此排序）、日文相似行对（同源复现，原句与其引述/复现形态）、日语侧引文回全文找出的疑似出处（引述回指；带 `relation` 证据分级 `exact／wraps／within／fuzzy`）。产物落 `--out` 目录（默认 `.cache/epub-work/echo-check/`），每作品一份 `*-呼应候选.md`。`--include-marker-quotes` 额外扫 `って／とか` 形态的改写式引述（候选量约 3 倍、需人工筛，只在通校收尾专查时开）。
- **逐条判定**：候选一律回日文原文核。先判**是否构成呼应**（两侧日文是否在说同一句话／同一说法／同一口癖；仅句式或词语碰巧相似的不算，写明理由排除）；构成呼应的再判**中文两侧是否一致、哪一侧偏离日文**。判定只取三种出口（§五 R5），与 R3 相同。引述点允许随语境调整人称、指示词与标点，**不许改关键措辞**。
- **差异性质决定「看什么」，不决定「改不改」**（§二.10）：`实词` 先核是不是真异译（同义改写同样会命中）；`语体` 先核日语侧是随口还是誓言——**中文两侧字形不同不等于必须统一**。
- **取形方向要看全库惯例，不能只看本卷**（`--convention "<日文正则>" --convention-words "<中文正则表>"`）。候选只说明「应当一致」，不说明往哪边一致。遇到**高频叙述定型**（同一表达在全库出现数十次以上，如 `息を吐く`、`微笑む`、`顔を上げる`）时尤其危险——卷内倾向可能与全库相反。实测 S5_03_02 卷内 `そっと息を吐く` 以「吐气」居多（26 行中吐气 14、叹气 10），据此把一处「轻叹一口气」改成「吐气」；而全库该说法是「叹气」占优（226 行中叹气 135、吐气 41），改动与全书相反，随后回退（`cbee10ca`）。词表词条按正则写（中文说法常被助词隔开，`叹[气了息]` 比「叹气」可靠），输出里的**分卷分布**用于识别例外卷、**未分类样例**用于补词表。**全卷倾向与全库相反时**：这类定型在卷内本就并存多种说法，单点改一处既建不起卷内一致、又会与全书惯例相左——按 R5 判「证据不足 → 待人工」或转术语统一流程，不要拿卷内多数当方向依据。
- **专项：引述升级**（工具按 `relation` 排序并把 `⤴升级` 置顶）。若某处被改成「引号内逐字复述原句」，必须回被引处确认原句措辞就是引述的版本；新引述指向一个并不存在的说法，是最难自查的一类断裂（历史案例见 §二.9 的「伤不了一根汗毛」与 `bbd38392`）。判据：`exact`（日语逐字同形）→ 中文必须一致；`wraps`（引述比被引处更完整）→ 被引处必须就是引述的那个版本；`within／fuzzy` → 措辞可不逐字一致，核语义与语气即可。
- **改写式引述（`って／とか` 形态，需开 `--include-marker-quotes`）**：日语两侧措辞本就不同、机械匹配找不到出处的引述，工具以「出处未定位」列出（中文侧仍保留引号与回指词）。这类**必须人工定位出处**——被引处往往是同一说法的另一种措辞，只改引述一侧就会断裂（S1_01 L290 即此型）。
- **覆盖要求**：机械候选只是入口，不是全集。机械信号抓不到的至少有三类——(a) 日文两侧措辞本就不同的引述（如原文 `疵一つつかない程度` 被后文引述为 `つかないんだよって`，两边用词不同，n-gram 相似度低）；(b) 叙述诡计与悬念（前文刻意含糊、后文才揭示，改动前文会毁掉后文）；(c) 跨卷引述（台词在别的卷被回指，本卷内查不到）。**因此：改动规模达到近重译级的卷（通校/重译/整批 `rewrite`），必须对全卷做呼应核查，不得只跑工具就宣布无断裂**；零散订正的按改动处所涉话题与人物做定向核查，并在报告里写明核查范围。
- **跨卷引述**：本卷内找不到出处的引文，按 `rg -n "<引文关键词>" EPUB` 在相邻卷（尤其同系列前作）与 `docs/translation-name-rulings.md` 里找，找到就按同一判据核；确实找不到出处的，写「未定位出处」，不要默认为「无问题」。
- **回改**：呼应断裂的回改与 R6 同一执行路径（显式映射 + 逐条预检、整批不写盘），同样是单写者串行；改哪一侧要看日文与上下文——原句侧偏离日文就改原句并向后传播，引述侧偏离就改引述侧，**不得为了「看起来一致」把两侧都改成第三版说法**。

**R4 回原文核对**（方法见 §七）。每条结论都要落到「中文位置 + 日文原句 + 判定」，写在报告里可复核。

**R5 判定与处置**，判定对象固定为「校对后的新译是否构成误改」，只有三种已核对出口：

- **保留新译**：新译成立；旧译同样成立也不能作为回退理由。有回改建议时明确「否决该建议」及理由，仍只计一个保留条目；
- **确认误改**：原文或规约证实有错，给出最小修正与依据；可以修成第三种正确表达，不机械退回旧译；
- **待人工**：证据不足，写明缺什么证据，不猜。

未实际核对的条目记 **未覆盖**，它是覆盖状态，不能算「保留新译」或冒充「待人工」。计数与落地状态按复核契约分开登记。

**R6 回改与门禁**：先按 `AGENTS.md` 运行写前同步；回改同属「改译文用词」，用 `translation-term-unification` skill 的执行器模板（显式映射 + 逐条预检，只改行内文字、不增删行），跑完过门禁：

进入写盘前须完成切片验收及 R3.5，解决待人工与未覆盖项。写前同步若改变了本轮输入，先按 R1 建新轮复核。门禁覆盖拟提交的整批成品，包含原校对改动、追加回改及规范化；没有额外回改也须验证原批次。只读任务止于报告，不执行本步及发布、暂存、提交。

```powershell
python tools/text_norm.py --dry-run             # 字符级规范化：必须 0 命中，有命中先 --apply 再复跑
python tools/check_alignment.py --strict        # 行模板 / 中日行数 / h2 / 图片行
python tools/check_epub_health.py --strict      # 单侧结构（XML / ruby / 加粗 / 悬空引用）
```

回改本身也是行内文字替换，只要动到加粗段附近就要重跑 `text_norm.py`：重译会重新划定 `<b>` 边界、把标点挪进加粗，而 `<b>` 段内含标点会同时卡住 `check_epub_health.py --strict` 与 `publish_auto.py` 发布预检（历史案例：创约9通校未重跑规范化，4 条 `bold-punct` 直接阻断写后同步，须先修复才能发布）。

**R7 同步、留档、提交**：

```powershell
python tools/publish_auto.py            # 打包上传 OneDrive + 回流缓存
```

- 复核产物与报告写本轮 `<report-root>`（不提交；`.cache/` 可随时删除重建，所以报告是工作产物而不是档案）。
- 报告的长期归属按 `AGENTS.md`「维护流程」的留档与提交项判定：复核引发的修改落在**两本及以上**书籍 → 写 `docs/maintenance-records/`；**单本**（如只动 `S3_01`）**不留档**，判定口径、统计与证据写进本次提交信息，由提交承载。
- **主智能体直接提交**：全部核对与回改验收完成、R6 门禁及写后同步成功后，由 Lead 依 [提交规范](references/commit-message.md) 编写中文 Conventional Commit 并直接执行本地提交，不再另等「请提交」；不推送。子智能体只交判定产物，不得暂存、提交或推送。
- 提交承载本批全部已确认且尚未提交的成品改动，包括保留的原校对修订与追加回改。即使追加回改为 0，只要原批次仍未提交，也须提交；历史复核无新增版本化变更时不创建空提交。
- Lead 按 R0 清单隔离暂存，只纳入本任务已复核内容；同文件混杂改动按补丁隔离，并保全原有无关暂存状态。检查实际 staged diff、`git diff --cached --stat` 与 `git diff --cached --check`，确认提交范围一致后执行；门禁、同步或提交失败时报告阻断原因，不宣称完成。
- 提交后核对 `git show --stat --oneline HEAD` 与 `git status`，报告提交号及仍保留的工作区改动；将主报告的提交状态更新为实际结果。
- 被否决的条目**不要**为了让报告「闭环」而硬改；它们的价值就是下次不再被误判；否决理由进提交信息或（跨本时）维护记录。

## 六、切片并行核对（R3 的执行方式）

语义级核对**强制交给子智能体、按切片并行**。多片按槽位并行，仅有一个合法切片时也须派一个子智能体，不能由 Lead 自办或为多开而拆散语义单元。子智能体须交回逐条判定、日文原文与覆盖明细，供 Lead 验收；分级判据（§四）、三种出口（R5）与全量要求不因并行而改变。

### 6.1 硬约束

1. **强制切片**：R3 的每一条语义级片段都必须经子智能体核对，不得以「片段少」「改动集中」「一眼能看完」为由由 Lead 自办；未开子智能体就宣称做完 R3，视为复核未完成。唯一例外是明确超出单切片视野的判定（§6.5 末），援引时必须在报告里写明是哪些条目、为什么。
2. **覆盖无缝无叠**：每条有效语义级片段 ID 必须恰归一个切片；计划 ID 集合恰等于清单的语义 ID 集合。只比较数量不构成验收，漏一条与重复一条不能抵消。
3. **不切断上下文**：切片边界只能落在「不可分割单元」之间（§6.2），不得把同一段落、同一场景或判定互相依赖的片段拆到两片。
4. **子智能体只读**：除本片结果文件外，不写 `EPUB/`、缓存书籍、裁定表或公共文件，不跑发布、规范化写盘及 Git 暂存／提交／推送。回改（R6）与 R7 由 Lead 串行执行，维持单写者。
5. **报告分片落盘**：每个子智能体只写 `<report-root>/slices/<slice-id>.a<attempt>.json`，严格使用复核契约的字段与枚举。主报告与汇总计数只由 Lead 生成。
6. **等齐再判定**：全部切片返回且状态明确之前**不输出任何结论性内容**（含「初步结论」「大方向」）；进度可以报，判定不给。
7. **故障即重发**：失败、中断、空结果或 §6.5 验收不合格，均按**同一轮、同一契约、同一边界**重发一次（`attempt=2`），保留旧产物但不计入有效结果。重发仍失败则全片记「未覆盖（子智能体故障）」；不能借其他片结论代填或直接进入 R6/R7。

### 6.2 定切法：先略读，再一次性划定

**切片前 Lead 必须先略读一遍待切片内容**，再定切法。略读范围是 `manifest.tsv` 的有效语义级全量条目（含 R2 重分类，不是只看文件清单）、`groups.txt` 聚类，以及涉及文件的实际上下文。略读产出三样东西：

- **工作量表**：按 `file` 聚合的**语义级片段数**与 diff 行数（不是文件数、不是文件体积）。这是装箱依据——只看文件数会把 2–3 倍的负载差带进切片，收尾必然参差。
- **不可分割单元清单**：需要共同语境才能判定的片段组成单元；同一最小差异模式、同一锚点尽量同片。单元超过硬上限时先按场景／引述关系细分，跨片明确只读共享上下文，条目归属仍唯一；无法可靠细分则报告计划阻塞，不能机械切开或放宽上限。
- **切片计划**：`slice id / 维度 / 所属条目 ID / 只读上下文 / 片段数 / diff 行数 / 文件数 / agent / 有效 attempt`，按 `slice id` 排序后写 `<report-root>/slices/plan.md`，**派发前一次定稿**。调度与有效 attempt 可更新，ID 归属与边界冻结。

计划一经派发即冻结，**不得边跑边切**。确需变更（漏切、错切、边界断义）时，先停掉全部在跑的切片，重新一次性定稿后整批重发；不得在运行中追加或改写切片。

### 6.3 切片策略（按优先级择一为主，可组合）

| 优先级 | 切片维度 | 切法 | 适用 | 不适用 |
| --- | --- | --- | --- | --- |
| 1 | **风险池** | `audit_risk.py` 标记（否定／数字／疑问／字形／加粗标点／嵌套引号／受控术语／明显增删）单独成片，先派、可加倍算力 | 任何批次 | —— |
| 2 | **作品** | 先按作品分组，再依硬上限切片；中日同一作品共同查证 | 跨本批次（≥2 本） | 单本任务 |
| 3 | **文件／内容序** | 以 `file` 为**边界**、按片段数装箱（§6.3 均衡规则）；默认同一文件不拆 | 单本、改动分散在多文件 | 改动集中在 1–2 个文件 |
| 4 | **模式（groups 聚类）** | 同模式尽量同片，超过硬上限按 §6.2 细分 | 同模式高频重复（整批 `rewrite`／统一替换） | 模式极多且各仅 1–2 条 |
| 5 | **术语锚点** | 同锚点尽量同片，片内逐处查证；跨片与全库计数由 Lead 统一核算 | 术语回退嫌疑（§二.5） | 批次内无术语改动 |

- **文件是边界，不是切片单位**：切片按片段数装箱，文件提供定位与上下文边界，允许合并小文件或按 §6.2 细分大文件；不能直接按文件数分配负载。
- 组合顺序：先切风险池 → 剩余 ID 再按作品切 → 作品内按**模式**或按片段数装箱。多风险条目只归一个切片、保留多个标签；单元含风险条目时将整个单元归入风险片，不能断义或重复派发。
- 粒度是**硬上限**：单切片同时满足 ≤ 150 条（语义片段或呼应候选按各自清单计）、≤ 3 个文件、≤ 400 行 diff——三项是**与**关系，任一超出就再切，不得用「一个子智能体全包」绕过。
- **按片段数均衡**：目标为每片 90–150 条、同风险池内片间最大／最小片段数 ≤ 2。小批次、尾片、单元边界或先触及文件数／diff 行数上限时允许不足 90 条，须在计划逐片注明原因；不得为凑数量跨越语义边界或突破硬上限。
- **单文件超上限时**：沿 §6.2 单元边界拆成所需片数，行号区间写死在计划里，所需上下文单列为只读；不得按字数或行数机械对半。
- **排序键**：`slice id` 用 `<作品>-<内容序起>[-<内容序止>]-s<两位序号>`（如 `S5_02_02-03-05-s01`），风险池用 `risk-01`、`risk-02`；全轮 ID 唯一，同一区间多片也不重名。计划按 `slice id` 排序，汇总与报告一律按**计划顺序**。
- **一个切片一个任务**：切片总数不设上限，按可用并发槽位分批派发，不将多片并入一个任务。先冻结全部计划再调度，不因槽位不足临时改边界。
- 各切片只报事实与判定，**不合并结论**；共同依据在不同条目上的适用性由 Lead 统一核验。

### 6.4 子智能体契约

派发时必须使用 [复核契约的固定任务模板](references/review-contract.md#二子智能体任务模板)，填齐本轮基准、所属 ID、上下文边界和唯一输出路径；不得只写「复核某卷」或仅转述目标。子智能体独立取证，不附带预设结论或其他片的判定。原文按 §七 的脚本读取；超出上下文才能判断的，先返回具体依赖，Lead 依 §6.2 决定是否重定计划，子智能体不自行扩片。

### 6.5 汇总：等齐 → 合并 → 统一判定

入口条件是**全部切片已返回且状态明确**（§6.1 第 6 条）；有切片在跑或状态未知时不进合并。合并按 `slices/plan.md` 的 `slice id` 顺序进行。然后由 Lead 串行做：

- **按计划顺序**：汇总、冲突登记与报告都按 `plan.md` 的 `slice id` 顺序（§6.3 排序键），**不按返回顺序、不按耗时**；谁先返回不改变任何判定。
- **结构验收**：逐片解析 JSON，核 `run_id / slice_id / attempt`、固定字段及判定枚举，检查返回 ID 无重复、无越界且恰等于分配 ID；日文引用、理由及最小修正符合契约。任一不符按 §6.1 重发，不以总数相等代替 ID 对账。越权写入时先保全并报告现场，不能继续落地该片结论。
- **归属与冲突**：同一 ID 出现两个所属切片即计划无效，回到 §6.2 重定计划；只读共享上下文不产生第二条判定。同锚点结论冲突时回原文裁决，不能取多数。
- **一致性对齐**：同一锚点在不同切片得出不同判定 → 以裁定表／译名选取规范统一，必要时回原文。
- **模式一致性**：可共享规则依据，但不同 ID 的原文与上下文须分别查实；模式传播不能产生已覆盖计数，也不能覆盖原有相反判定。
- **覆盖率核算**：按契约公式从有效结果逐 ID 派生计数，未覆盖项（含故障切片）和待人工项全部列明；存在任一项即未完成，不能进入自动提交。
- **原文验收**：Lead 逐条回打所有「确认误改」及措辞统一建议的原文，确认最小修正成立；另对每片「保留新译」按 ID 顺序取首、末及风险最高的 3 条去重抽检（不足则全检，风险按 R3 的顺序、同级按 ID）。发现引用不符、行号错位或判定站不住，按 §6.1 整片重发。
- **全库计数只能串行做**：回改前后对每个新形／旧形做全库计数（§九「回改方向与库内多数形相反」），子智能体的局部计数不构成全库证据。
- **串行例外仅限全局视野判定**：全库计数、引句取形、跨切片一致性这类明确超出单切片视野的判定由 Lead 串行做（§6.1 第 1 条的唯一例外）；不得用它把 R3 的逐条核对收归 Lead，援引时必须在报告写明条目与理由。
- **回改串行**：R6 由 Lead 按显式映射 + 逐条预检执行，整批预检不过则不写盘。

### 6.6 不派片的边界（仅限以下情形）

- **`spec` 级放行**不派片：R2 已确认子类与规范一致的记录由 Lead 批量放行；一旦某条被重新判为语义级，立即纳入切片。
- **全局视野判定**不派片：全库计数、引句取形、跨切片一致性由 Lead 串行做（§6.5 末）。
- **R6 回改与 R7 同步、提交**不并行：单写者，绝不并行。

除上述三项外**任何理由都不成立**——「片段少」「改动集中在单个文件」「一眼能看完」「依赖前一轮结论」「先自己过一遍再决定要不要派」都是绕过强制切片的借口。回改后由子智能体按本轮回改前后差异验收，清单生成方法见复核契约；使用新轮 ID 并回指原条目，只核新增／改写条目及受影响呼应。若日文参考或其他输入发生变化，还须重核此前已判定但证据受影响的 ID，不能只验回改清单；不能可靠圈定影响范围时重核本轮全部条目。验收仍发现误改则继续修正，全部验收完成才进入 R7。

## 七、回原文核对的方法

**配对**：中日两侧按同一作品号配对；文件按**内容序 NN** 一一对应（内容序是对齐顺序，不由章名反推）。文件内部按同一物理行定位；先验证内容序与行数对齐，再使用 `proofread_review.py` 的 `jp` 列或 `japanese_lookup.py` 取对应原文。若门禁未过、历史版本发生行数变动或结果不对应，按关键字与上下文确认，不能把错误的同行文本当证据。

路径（注意两侧目录结构不同）：

```
日文：.cache/epub-work/japanese-text/【S3_01】創約 とある魔術の禁書目録(01)/item/xhtml/S3_01-07.xhtml
中文：EPUB/【S3_01】创约 某魔法的禁书目录 01/OEBPS/Text/S3_01-07_Chapter3.xhtml
```

取纯文本要**先剥 `<rt>` 注音再 `text_of`**——`xhtml_text.text_of` 只去标签，不剥注音，带注音的词会被拆成「魔術 まじゆつ」而检索不到。用本 skill 附带的查证脚本（已封装路径、内容序、剥注音）：


几条纪律：

- **引用原文时必须连同内容序与实际句子一起写**，报告里的「日文原文」列要能被人直接检索到。
- 同一词在同卷多处出现时，逐处看：卷内一致性本身就是判定依据（例：`ステーションワゴン` 同卷一处译「旅行车」、一处译「小货车」→ 异译）。
- 原文分两级写法时不要合并判定（例：`念動能力` 与 `念動力` 是两个词，前者可作「念动能力」）。
- 检索脚本放临时目录，跑完删除，不提交；只针对本次任务的批量导出／比对脚本属一次性脚本，不进 `tools/`。

## 八、报告模板

Lead 必须按 [复核契约的固定主报告模板](references/review-contract.md#四主报告模板) 写 `<report-root>/review-summary.md`，章节顺序、状态枚举及统计口径固定；空项写「无」或「未执行＋原因」，不删除栏目，不用「第 N 轮」不断追加新章节。

报告由本轮清单、有效子报告和实际执行结果生成：问题与待办全列 ID，保留新译只列必要样例并链接完整切片结果；不复制整章译文。对话回复给出状态、覆盖分母、回改数量、阻断项或提交号及报告路径，不用「100%」「全部通过」代替证据。单本长期证据与跨本留档仍按 R7 归属处理。

## 九、坑清单

| 坑 | 规避 |
| --- | --- |
| 引用原文行号与实际句子不一致 | 写「建议回改」前，用脚本把该行原文打出来核对（§七） |
| 按日文字面判术语对错 | 先查规约与 `translation-term-unification` 的已裁定结论索引 |
| 建议补上原文刻意省略的成分 | 看后文是否揭示；刻意留白一律否决 |
| 把 `tiny` 当「可跳过」 | 术语／事实改动的字数也可能只有 2 字 |
| 用「只差标点」的直觉放行数字改动 | 数字不是标点，事实层逐条核 |
| 抽样后就宣布整批通过 | 结论里必须写明未覆盖范围（尤其明显删减） |
| 只剥标签不剥 `<rt>` 就检索 | 用 §七 的脚本；带注音的词会被拆开 |
| 用 `glob` 匹配书目录名 | 作品号定界符 2026-10-12 起为全角 `【…】`，不再是 glob 的字符类；旧的半角 `[…]` 形态已废弃，历史提交里的路径照旧要按字符类处理 |
| 为复核历史提交新建 worktree | 工具直接读 git 历史，不需要额外工作树 |
| 把复核报告写进仓库或别的 agent 的工作目录 | 工作产物放 `.cache/epub-work/proofread-review/`；需要长期保留的结论按「维护流程」的留档与提交项进 `docs/maintenance-records/`（跨本）或提交信息（单本） |
| 复核报告自己的结论不再核对 | 报告自身也要回原文核（第二轮修正的教训） |
| 只把「看着像术语」的条目拿去比规约 | 通校／重译一律做全量比对（§二.5），且三处来源都要扫：裁定表、译名选取规范（§一 已选定名单、§四 防日语中转）、翻译规范。创约9 的 6 处「恶女」回退与 2 处「黛安·福琼」都藏在整批 `rewrite` 里 |
| 据旧译反推日文原文 | 旧译本身就是被复核对象，不能当原文证据；凡引用日文必须用 §七 脚本实打实打出来（§二.6 案例二） |
| 改完整行却不重跑字符级规范化 | 重写会重新划定 `<b>` 边界、把标点挪进加粗；R6 必跑 `text_norm.py --dry-run` 并确认 0 命中，别等发布预检或 CI 才发现 |
| 回改时把前一轮刻意定下的写法改掉 | 回改前对每条原串跑 `git log -S '<原串>' -- <文件>`，命中**非批量导入**的既有提交（尤其 `fix(...) 通校／复核／统一` 类）就先读该提交信息。历史案例：`わーい、ミサカがミサカが一番乗り` 已由 `5168175b` 定为「好耶，御坂御坂第一个吃上！」（该提交专门把最后之作的 9 种开场感叹分层，避免与固定口癖 `いやっほう` 混淆），引句统一批次 2 却改成「哇啊，御坂御坂第一个到！」，回退了既有决定 |
| 回改方向与「库内多数形」相反 | 回改后对每个新形／旧形做全库计数（`rg -o --no-filename <形> EPUB \| Measure-Object`）：新形应≥旧形且旧形归零。旧形仍有残留时先分辨是同源词的其他译法，还是既有统一提交的回退残留（如 `5da0bc5f` 统一 `FIVE_Over` 后 `S2_11-09` 仍留 9 处 `Five_over`）。历史案例：引句统一批次 3 按提案把「诸神之门」取成「自天而降」，终检发现全库另有 29 处作「从天而降」，只得撤回取形 |
| 略读不足导致切片断义 | 切片前略读清单的有效语义全量条目与 `groups.txt`，列出语义单元及只读共享上下文（§6.2） |
| 边跑边切 | 切片计划派发前一次定稿并冻结；确需变更先停掉全部在跑的切片、重新一次性定稿后整批重发（§6.2） |
| 切片边界重叠或漏切 | 按有效语义 ID 集合及唯一性核对归属与返回结果；重复归属须重定计划，不能按优先级去重后当作通过 |
| 切片未齐就出结论 | 全部切片返回且状态明确后才进合并；未齐时只报进度，不给判定（含「初步结论」） |
| 子智能体故障被静默跳过 | 按同一契约、同一边界重发，不得改边界或用其它切片外推代填；仍失败则整片记入「未覆盖（子智能体故障）」 |
| 各切片各写公共报告互相覆盖 | 只写本片 `slices/<slice-id>.a<attempt>.json`；公共报告只由 Lead 汇总写 |
| 子智能体顺手改了 `EPUB/` | 契约里硬禁止；回改只有 Lead 一个写者（R6） |
| 用并行切片代替全量，把抽样说成全量 | 每个分配 ID 恰一条有效结果，未实际查证只记未覆盖；Lead 从有效结果派生计数 |
| 各切片取到不同原文版本／行号基准 | prompt 写死 `--jp-base` 与基准 commit |
| 子智能体把局部计数当全库证据 | 全库计数（新形 ≥ 旧形、旧形归零）由 Lead 串行做 |
| 以「量小／一眼能看完／先自己过一遍」为由不派子智能体 | R3 强制切片（§6.1 第 1 条）；未开子智能体即视为复核未完成——报告「切片与覆盖」表里语义级片段数 > 0 而切片数为 0，直接判未完成 |
| 只信子智能体的结论、不回打原文 | 误改及措辞建议逐条复打，保留项按固定规则抽检；不符按 §6.1 整片重发（§6.5） |
| 按现成的文件结构一文件一片 | 切片单位是**片段数**，文件只是边界（§6.3）。一文件一片 = 没做切片，只是把整本书摊开；零改动的文件还会空转一片 |
| 只按文件数装箱导致片间负载悬殊 | 按片段数均衡、三项硬上限同时满足；小批次／尾片等例外逐片写明原因（§6.3） |
| 汇总按返回顺序 | 按 `plan.md` 的 `slice id` 顺序合并与报告，不按返回顺序、不按耗时（§6.5） |
| 子智能体通读整章／整本 | 只读片段清单与最小上下文窗口，原文按行号或关键词取（§6.4）；用量与工作量不成比例即为信号 |
