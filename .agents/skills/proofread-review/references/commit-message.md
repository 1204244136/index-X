# 校对复核提交规范

文档职责与入口见 [文档索引](../../../../docs/README.md)。本规范用于 [R7](../SKILL.md) 的成品提交，提交前必读；不用于修改 skill 或工具本身的提交。

## 标题

校对复核的成品提交统一使用 `fix(epub)`，中文标题；作品号写在标题正文，不用卷号作 scope，不因整卷通校而改用 `feat`。

```text
fix(epub): <范围> 校对复核与修正
fix(epub): <范围> 校对复核确认批量修订
```

有复核追加回改／规范化时用第一种，没有追加修正但有原批次待提交时用第二种。单本 `<范围>` 用完整作品号（如 `S1_13`、`S5_03_02`、`S6_YY.MM.DD`），跨本用 `<N> 本`，完整编号在正文列全。标题不用完整书名、案例清单或回改数量堆叠，不混用「通校优化／复审／落库／落地」命名同一流程。

## 正文

固定按「范围 → 复核 → 修正 → 验证 → 同步」排列，跨本最后加「留档」。以下是字段模板，数字和命令结果均取自本轮有效报告，不能照抄历史数值：

```text
fix(epub): <范围> 校对复核与修正

- 范围：<完整作品号列表>，<N> 个 EPUB 文件（其中 XHTML <N> 个）；对象为<工作区相对基准 SHA / 历史提交列表>；提交包含<整批已确认校对修订及追加修正 / 仅历史复核追加修正>。
- 复核：总片段 <T>，有效规范级 <S>、语义级 <M>；<切片数> 片逐条回查日文；保留新译 <K>、确认误改 <R>、待人工 0、未覆盖 0；<关键保留/否决依据>。
- 修正：追加回改 <N> 个位置，涉及<主要问题类型>；<少量关键位置、旧→新及日文/规约依据>；规范化 <N> 处命中；<回改验收结果，或无额外回改>。
- 验证：<实际执行的完整命令名、关键参数、范围与结果>；术语比对及呼应<核查范围、候选已判定数/总数及结果>。
- 同步：python tools/publish_auto.py 写后同步成功，<实际发布作品数及回流结果>。
- 留档：docs/maintenance-records/<记录文件>（仅跨本保留本行）。
```

正文须能脱离本地缓存报告理解：单本把关键原文／规范依据和否决理由写进提交，跨本保留结论并引用维护记录。只摘必要短句，不搬运全量逐行报告。未发生的动作不写成已完成；正文中的「修正」描述最终差异，不能把曾尝试但已撤回的方案列为成果。

计数遵循 [复核契约](review-contract.md)：审计片段取冻结基线，文件数取实际提交范围，追加回改取去重位置。原通校改动与复核追加回改要分别交代，避免把包含上千处通校修订的提交只描述成「回改十余处」。风险标签不求和，规范化命中不混称回改位置；呼应等专项与语义片段分开统计。

## 执行与收尾

- 只有 Lead 执行 R7 的范围核验、暂存和提交；前置条件及用户限定以 skill 为准。多行提交信息先写系统临时文件，使用 `git commit -F <文件>` 保留真实换行。
- 提交前核 staged diff 与统计；提交后核实际 SHA、文件范围和剩余工作区状态。对话报告 SHA、标题及未推送，不把「已生成提交信息」当作已提交。
- 无版本化变更不创建空提交，不为统一历史风格重写既有提交。
